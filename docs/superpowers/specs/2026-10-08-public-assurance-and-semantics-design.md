## Verified current `kadmos.world.v0` contract

This section records the current implementation, including limitations. It does not prescribe silent semantic changes.

* **Parsing and admission.** `parseWorldSpec` in `src/world_compiler.ts` accepts a deliberately restricted indentation-based YAML subset, not arbitrary YAML. Version must be `kadmos.world.v0`; exactly one initial state is required; state and transition IDs must be unique; transition endpoints must exist; transitions cannot leave a declared terminal state. Context types are `integer` and `string`. Integer bounds/defaults must be JavaScript safe integers; integer minimum is nonnegative when supplied, default is 0 when omitted, and strings require a string default without numeric bounds. Declared identifiers in predicates, guards, and effects are checked; expression well-typedness is generally established only at execution. The parser does **not** insert `directive: null` when a World transition omits `directive`. That omission is a known cross-language defect: emitted TS returns `UNAUTHORIZED_DIRECTIVE` for a request with no proposed directive, while emitted Python raises `KeyError` before a verdict and restores its checker state. It is separate from a request that omits or misstates `proposedDirective` against a World transition whose directive is explicitly declared. The parser does not prove all invariants or all legal paths.
* **Expressions.** `src/world_expression.ts` and emitted evaluator implement literals (`true`, `false`, `null`, nonnegative decimal numerals, single-quoted strings), identifiers, property access, grouping, unary `!`/`-`, arithmetic, comparison, equality, `&&`, `||`, and right-associative `=>` by precedence climbing. Logical operators evaluate both operands and require booleans; they do not short-circuit. Numeric operations use JavaScript numbers/IEEE-754; division by zero may yield non-finite values. A falsy property base resolves to null; equality can compare non-finite results without rejecting them, while numeric operators requiring a finite operand or integer effect/context checks can refuse them. Python's division helper also yields infinity/NaN for zero divisors. Missing properties resolve to null, while a missing top-level identifier is not made valid by declaration checking alone. Guards and invariants must evaluate to exact boolean true. Effects execute **in listed order**, with later effects seeing earlier candidate-context updates and the destination `state`.
* **Steps.** A request uses `transitionId`, optional `eventPayload`, and optional `proposedDirective`; the README/skill `payload` spelling is not recognized. The generated checker validates request primitives and sanitizes object payloads, refusing proxies, accessors, non-plain objects, reserved keys, cycles/shared nodes and excessive depth/node count. Payload booleans, fractions and unsafe numbers are copied as primitives; the sanitizer does not require every payload number to be an integer. Integer type/safe-range refusal occurs if such a value reaches an integer effect or context reset/bounds check; guards may instead refuse by their own expression result. Reserved keys `__proto__`, `constructor`, and `prototype` are sanitizer-time refusals. It does not coerce malformed request fields to valid ones. From the current state, it checks the named transition, exact proposed directive, guard, sequential effects and their types, context bounds, then all post-state invariants. A refusal returns `allowed: false`, unchanged checker state/context/history, null `directiveAllowed`, a violation code, and accepted-history-plus-attempt trace. An accepted step commits checker state/context/history and reports the declared directive. Terminal-state illegal attempts are refused. The checker is synchronous and has a reentrancy guard during evaluation; it does not serialize separate asynchronous Fabric operations.
* **Reset and rollback.** Generated TS `reset()` validates a candidate initial context and initial-state invariants before publishing; a failed reset preserves state/context/history. Successful reset clears history and the savepoint. Generated TS `rollbackLastStep()` restores the single most recent successful step's checker state/context/history and consumes its savepoint; it throws `NO_CHECKER_SAVEPOINT` if absent or busy. A rejected step leaves an earlier successful savepoint intact: calling rollback on rejection can therefore undo accepted work. A subsequent successful step replaces that savepoint. The generated TS class has the method, but emitted `ports.d.ts` `IWorldChecker` omits it. The interpreted checker (`src/world_checker.ts`) and generated Python checker have no public post-success rollback method. Their internal rejection rollback is separate. Document this asymmetry as a defect, not parity.
* **Python comparison.** Generated Python admits exact-dict requests, rejects malformed primitive types, uses float64 for expression arithmetic and safe-integer checks for integer context; its `step()` returns the corresponding verdict dictionary and restores internal state on rejection/exception. Its generated `ports.py` has no rollback method. Current differential fuzzing compares a TS **interpreted** checker with generated Python, not the emitted TS checker, and only the generated requests/verdict fields it observes. It does not exercise external side effects, all expression inputs, or post-success rollback.

Meaningful conformance tests should compile and execute emitted TypeScript and Python checkers against the same hand-authored Worlds and traces, and compare expected outcomes as well as each other. Every normal fixture transition explicitly declares its directive, using `directive: null` when none is authorized. Test sequential effects (including destination-state visibility), integer boundaries and overflow, exact request-field admission versus payload copying, refusal preserving prior accepted history, directive matching, reset, and generated TS rollback. Include one deliberate omitted-World-directive characterization: TS refusal versus Python `KeyError` with no state mutation; do not silently fix either generator. Mark Python post-success rollback as an expected capability gap, not a test to fake. Keep an independent expected oracle for each case; TS/Python agreement alone can preserve a shared bug. Any observed mismatch or unsafe acceptance becomes a separately reviewed behavior-change proposal with a failing regression, not an undocumented “contract” update.

## Fabric example design

The README World currently writes its context definitions as inline `{ type: ... }` maps. `parseWorldSpec` rejects those inline maps in its restricted YAML subset. Expand them to supported indented mappings before treating the example as executable; this is a documentation correction, not a parser change.

Replace the README's non-existent `createWorldChecker()` zero-argument use, `payload` key, rejection rollback, and undefined `db`. First add `directive: null` to `CONFIRM_PAYMENT` and every other no-directive World transition shown in README or skill examples; omitted World directive is not equivalent to null in the current generators. The smallest honest example uses that compiled World and `new WorldChecker()` from `./world/world_checker.js`, `CONFIRM_PAYMENT` from `CREATED`, no request `proposedDirective` (or explicit null), and `eventPayload: { captured_amount: amount }`. It accepts an injected `persist(orderId, state): Promise<void>` callback to avoid pretending a database API exists. On refusal it throws without rollback. After an allowed step it calls `persist` in `try`; on thrown physical failure it immediately calls `checker.rollbackLastStep()` and rethrows. A per-checker Promise chain serializes calls across the `await`, recovers after a rejection, and propagates the original error to its caller; the text says all users of that checker must use that chain. Explain that rollback only restores checker memory, and a callback that commits then reports failure needs its own compensation/idempotency/transaction design. This example makes no external atomicity guarantee. Test the actual extracted or shared fixture by compiling and executing it against a generated checker: accepted then rejected preserves accepted state; on the **same checker**, a first allowed step followed by failed persistence rolls back to `CREATED`, its caller receives the rejection, and a queued later call then succeeds and commits. Avoid a brittle text-only snapshot as sole evidence.

The published skill's TypeScript and Python examples both use `payload` and rollback on rejection; the Python snippet calls a method that does not exist and uses `from world.world_checker import WorldChecker` where scaffolded Python instead adds `src/world` to `sys.path` and imports `world_checker`. Correct the TS pattern and use a real Python import/path if any Python snippet remains; remove or accurately qualify the Python post-success example until a separate Python rollback design is accepted. The skill's `kadmos infer --prd <spec.md>` is invalid: `infer` takes `<file>`; `--prd` belongs to `run`. `kadmos legislate` takes requirements prose through `inferBoundary`, not an already compiled World YAML. Audit `src/cli.ts` usage and `src/scaffold.ts` import pattern, then correct both skill commands. Audit `examples/` and scaffolded worker text for the same guarantee language; change only misleading public material in this batch. Keep generated source untouched. Do not expose private task IDs in README, skill, or the future public semantics doc.

## Phases and later gates

1. **Public assurance claims (first batch):** README and packaged skill wording map to the evidence table; no unsupported proof/atomicity/shortest-path promise remains. Acceptance: focused claim audit plus full `pnpm run verify`.
2. **Fabric rollback examples (first batch):** executable TS example follows the actual generated API, serializes one checker, leaves rejection untouched, rolls back promptly after failed physical work, and states external limits. Acceptance: real checker execution for refusal, failure, success and overlapping calls; skill audit.
3. **World semantic contract (first batch):** `docs/` current-behavior contract plus TS/Python generated-checker tests, independent expectations and a defect register. Acceptance: deterministic tests for the behaviors listed above, `pnpm run verify`, `pnpm run test:fuzz`; no silent compiler behavior change.
4. **Release/Quick Start/MCP (first batch):** clean tarball consumer follows public instructions and stdio MCP tools. Acceptance: reproducible isolated smoke test, dry-run pack file audit, supported runtime matrix evidence when CI runs. No publish or tag in this batch.
5. **Harmonia correspondence integration (later):** depends on accepted priorities 1–4 and separately resumed T-396. Define source World-to-reference semantics and emitted checker-to-target implementation correspondence obligations, with independent reviewer acceptance and counterexamples. Done only after real correspondence evidence, never inferred from differential fuzzing. Do not touch Harmonia in this batch.
6. **Real Fabric fault handling (later):** depends on documented rollback limits and explicit persistence/transaction design. Inject crashes, partial commits, retries, concurrency and process boundaries in a real adapter; demonstrate compensation or atomic persistence and recovery with physical failure evidence. Checker rollback alone is insufficient.
7. **Templates and diagnostics (later):** depends on stable semantic examples and fault outcomes. Extend optional templates, actionable violation diagnostics and repair guidance with user-facing tests; preserve accepted World authority and existing scaffold choices.
8. **Composition and other verification backends (later):** depends on a stable reference semantics and separately reviewed interface contracts. Specify cross-World composition obligations and backend trust/equivalence criteria before implementing SMT/model-checker or other backends; acceptance requires sound mappings and counterexample validation, not marketing parity.
