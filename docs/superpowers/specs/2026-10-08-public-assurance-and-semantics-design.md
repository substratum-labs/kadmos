## Verified current `kadmos.world.v0` contract

This section records the current implementation, including limitations. It does not prescribe silent semantic changes.

* **Parsing and admission.** `parseWorldSpec` in `src/world_compiler.ts` accepts a deliberately restricted indentation-based YAML subset, not arbitrary YAML. Version must be `kadmos.world.v0`; exactly one initial state is required; state and transition IDs must be unique; transition endpoints must exist; transitions cannot leave a declared terminal state. Context types are `integer` and `string`. Integer bounds/defaults must be JavaScript safe integers; integer minimum is nonnegative when supplied, default is 0 when omitted, and strings require a string default without numeric bounds. Declared identifiers in predicates, guards, and effects are checked; expression well-typedness is generally established only at execution. The parser does not prove all invariants or all legal paths.
* **Expressions.** `src/world_expression.ts` and emitted evaluator implement literals (`true`, `false`, `null`, nonnegative decimal numerals, single-quoted strings), identifiers, property access, grouping, unary `!`/`-`, arithmetic, comparison, equality, `&&`, `||`, and right-associative `=>` by precedence climbing. Logical operators evaluate both operands and require booleans; they do not short-circuit. Numeric operations use JavaScript numbers/IEEE-754; division by zero may yield non-finite values, later refused where a number is required. Missing properties resolve to null, while a missing top-level identifier is not made valid by declaration checking alone. Guards and invariants must evaluate to exact boolean true. Effects execute **in listed order**, with later effects seeing earlier candidate-context updates and the destination `state`.
* **Steps.** A request uses `transitionId`, optional `eventPayload`, and optional `proposedDirective`; the README/skill `payload` spelling is not recognized. The generated checker validates request primitives and sanitizes object payloads, refusing proxies, accessors, non-plain objects, reserved keys, cycles/shared nodes and excessive depth/node count. It does not coerce malformed request fields to valid ones. From the current state, it checks the named transition, exact proposed directive, guard, sequential effects and their types, context bounds, then all post-state invariants. A refusal returns `allowed: false`, unchanged checker state/context/history, null `directiveAllowed`, a violation code, and accepted-history-plus-attempt trace. An accepted step commits checker state/context/history and reports the declared directive. Terminal-state illegal attempts are refused. The checker is synchronous and has a reentrancy guard during evaluation; it does not serialize separate asynchronous Fabric operations.
* **Reset and rollback.** Generated TS `reset()` validates a candidate initial context and initial-state invariants before publishing; a failed reset preserves state/context/history. Successful reset clears history and the savepoint. Generated TS `rollbackLastStep()` restores the single most recent successful step's checker state/context/history and consumes its savepoint; it throws `NO_CHECKER_SAVEPOINT` if absent or busy. A rejected step leaves an earlier successful savepoint intact: calling rollback on rejection can therefore undo accepted work. A subsequent successful step replaces that savepoint. The generated TS class has the method, but emitted `ports.d.ts` `IWorldChecker` omits it. The interpreted checker (`src/world_checker.ts`) and generated Python checker have no public post-success rollback method. Their internal rejection rollback is separate. Document this asymmetry as a defect, not parity.
* **Python comparison.** Generated Python admits exact-dict requests, rejects malformed primitive types, uses float64 for expression arithmetic and safe-integer checks for integer context; its `step()` returns the corresponding verdict dictionary and restores internal state on rejection/exception. Its generated `ports.py` has no rollback method. Current differential fuzzing compares a TS **interpreted** checker with generated Python, not the emitted TS checker, and only the generated requests/verdict fields it observes. It does not exercise external side effects, all expression inputs, or post-success rollback.

Meaningful conformance tests should compile and execute emitted TypeScript and Python checkers against the same hand-authored Worlds and traces, and compare expected outcomes as well as each other. Test sequential effects (including destination-state visibility), integer boundaries and overflow, strict request/payload admission, refusal preserving prior accepted history, directive matching, reset, and generated TS rollback. Mark Python post-success rollback as an expected capability gap, not a test to fake. Keep an independent expected oracle for each case; TS/Python agreement alone can preserve a shared bug. Any observed mismatch or unsafe acceptance becomes a separately reviewed behavior-change proposal with a failing regression, not an undocumented “contract” update.

## Fabric example design

Replace the README's non-existent `createWorldChecker()` zero-argument use, `payload` key, rejection rollback, and undefined `db`. The smallest honest example uses the README's compiled World and `new WorldChecker()` from `./world/world_checker.js`, `CONFIRM_PAYMENT` from `CREATED`, and `eventPayload: { captured_amount: amount }`. It accepts an injected `persist(orderId, state): Promise<void>` callback to avoid pretending a database API exists. On refusal it throws without rollback. After an allowed step it calls `persist` in `try`; on thrown physical failure it immediately calls `checker.rollbackLastStep()` and rethrows. A per-checker Promise chain serializes calls across the `await`; the text says all users of that checker must use that chain. Explain that rollback only restores checker memory, and a callback that commits then reports failure needs its own compensation/idempotency/transaction design. This example makes no external atomicity guarantee. Test the actual extracted or shared fixture by compiling and executing it against a generated checker: accepted then rejected preserves accepted state; allowed then failed persistence restores checker state; overlapping calls are serialized; success remains committed. Avoid a brittle text-only snapshot as sole evidence.

The published skill's TypeScript and Python examples both use `payload` and rollback on rejection; the Python snippet calls a method that does not exist. Correct the TS pattern and remove or accurately qualify the Python post-success example until a separate Python rollback design is accepted. Audit `examples/` and scaffolded worker text for the same guarantee language; change only misleading public material in this batch. Keep generated source untouched.

## Release and clean-consumer design

`package.json` exposes `bin/kadmos.js`, `bin/kadmos-mcp.js`, root and BullMQ exports, and the files allowlist `bin`, `dist/src`, `skills`, `README.md`, `LICENSE`. `src/scaffold.ts` emits default/order-settlement/circuit-breaker starter Worlds, dual checker files, workers and scripts. Existing `tests/test_release_hygiene.test.ts`, `tests/test_scaffold.test.ts`, and `tests/test_mcp_server.test.ts` cover in-repo cases. The new gate must build and pack a tarball, inspect its allowlist, install that tarball in a temporary clean consumer (no linked repo `node_modules`), run the documented CLI demo/init/compile/test route under supported Node/Python, compile and run starter TS/Python workers, and exercise both `kadmos mcp` and `kadmos-mcp` with JSON-RPC initialize/tools/list/one tool call over stdio. Use package-local binaries from the installed tarball and a local temp registry-free install; do not claim the network `npx` path works unless separately checked. Check the generated Quick Start against the exact scripts `src/scaffold.ts` emits; correct documentation or scaffold only for a reproduced discrepancy. `pnpm pack --dry-run` and package file-list checks remain mandatory.

## Phases and later gates

1. **Public assurance claims (first batch):** README and packaged skill wording map to the evidence table; no unsupported proof/atomicity/shortest-path promise remains. Acceptance: focused claim audit plus full `pnpm run verify`.
2. **Fabric rollback examples (first batch):** executable TS example follows the actual generated API, serializes one checker, leaves rejection untouched, rolls back promptly after failed physical work, and states external limits. Acceptance: real checker execution for refusal, failure, success and overlapping calls; skill audit.
3. **World semantic contract (first batch):** `docs/` current-behavior contract plus TS/Python generated-checker tests, independent expectations and a defect register. Acceptance: deterministic tests for the behaviors listed above, `pnpm run verify`, `pnpm run test:fuzz`; no silent compiler behavior change.
4. **Release/Quick Start/MCP (first batch):** clean tarball consumer follows public instructions and stdio MCP tools. Acceptance: reproducible isolated smoke test, dry-run pack file audit, supported runtime matrix evidence when CI runs. No publish or tag in this batch.
5. **Harmonia correspondence integration (later):** depends on accepted priorities 1–4 and separately resumed T-396. Define source World-to-reference semantics and emitted checker-to-target implementation correspondence obligations, with independent reviewer acceptance and counterexamples. Done only after real correspondence evidence, never inferred from differential fuzzing. Do not touch Harmonia in this batch.
6. **Real Fabric fault handling (later):** depends on documented rollback limits and explicit persistence/transaction design. Inject crashes, partial commits, retries, concurrency and process boundaries in a real adapter; demonstrate compensation or atomic persistence and recovery with physical failure evidence. Checker rollback alone is insufficient.
7. **Templates and diagnostics (later):** depends on stable semantic examples and fault outcomes. Extend optional templates, actionable violation diagnostics and repair guidance with user-facing tests; preserve accepted World authority and existing scaffold choices.
8. **Composition and other verification backends (later):** depends on a stable reference semantics and separately reviewed interface contracts. Specify cross-World composition obligations and backend trust/equivalence criteria before implementing SMT/model-checker or other backends; acceptance requires sound mappings and counterexample validation, not marketing parity.
