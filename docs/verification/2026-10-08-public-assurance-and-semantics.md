## Windows test portability follow-up

Source PR 10's initial CI run **37868247928** failed in eight Windows jobs (Node 20/22 × Python 3.10–3.13). The log at `/private/tmp/kadmos-public-windows-r1.log` lines 1259–1290 shows `test_packed_quickstart` failing immediately on `spawnSync("npm", ["pack", ...])`: `status`, `stdout`, and `stderr` were null; the previous helper discarded `result.error`. The earlier 241 tests and other new semantic/example tests passed in those jobs. This was one demonstrated portability failure repeated across the matrix, not eight independent product defects. The subsequent run on the fix is recorded below.

[Node's child-process documentation](https://nodejs.org/download/release/v22.23.3/docs/api/child_process.html#spawning-bat-and-cmd-files-on-windows) explains that Windows `.cmd` files cannot be executed directly as native child programs without a shell. The failing test invoked raw `npm` and later raw `pnpm` through `spawnSync` without a shell. The working `scripts/test-packed-types.js` pattern instead runs `process.execPath` with pnpm's `npm_execpath` JavaScript CLI. The localized fix uses that pattern for packing and all pnpm commands, preserving each argument as its own array element (including a temp path with spaces); it avoids shell concatenation. `pnpm --config.ignore-scripts=true pack` produced a tarball locally without prepack recursion, and a separate `pnpm pack --dry-run` continues to test prepack. The test now lists files from the extracted tarball, includes `result.error` in failed-spawn diagnostics, and parses MCP responses with minimal explicit types rather than `any`. Windows `tar` remains exercised, not skipped; the existing packed-types probe also uses `tar`. NODE_TEST_CONTEXT was left to normal child-process inheritance. The subsequent successful matrix run exercised this inheritance and tar extraction on Windows as well.

## Current behavior and known deficiencies

The generated-checker tests use explicit `directive: null` for ordinary no-directive Worlds. The deliberately omitted-directive case exposed more than a runtime verdict difference: emitted TypeScript fails strict typecheck on `.directive`; emitted JavaScript, when produced despite that diagnostic, refuses a no-directive request with `UNAUTHORIZED_DIRECTIVE`; generated Python `ports.py` contains invalid `Literal[]` syntax and fails import before its checker body can raise the latent `KeyError`. An empty invariant list likewise fails emitted TypeScript strict typecheck. These are characterized in `docs/world-semantics-v0.md`; this batch did not change the generators or generated files.

The generated TypeScript checker has one post-success rollback savepoint, but generated `ports.d.ts` omits it from `IWorldChecker`; generated Python and interpreted TypeScript expose no matching public post-success rollback method. Rollback only restores checker memory. The README example is a single modeled lifecycle with a serialized checker; it does not establish external or cross-process atomicity.

The CLI and public demo wording now report observed traces and sampled differential results. The BullMQ README paragraph describes the actual `transitionJob` Redis Lua mechanism without claiming a verified replacement of all BullMQ scripts. Manual claim review covered README, the packaged skill, CLI output, and the packed demo; no marketing-string-only tests were added. Later Harmonia correspondence, real Fabric fault handling, templates/diagnostics, and composition/backends remain outside this implementation.
